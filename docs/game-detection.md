# 游戏进程白名单检测

本页保留旧名单模式。最新 [无白名单自动识别](automatic-game-detection.md) 已提供自动目录和多信号策略，不再要求手工配置游戏EXE；旧模式仍可作为兼容选项，两个模式不能同时开启。

日期：2026-11-01，Asia/Shanghai。本轮在已有 GPU Resource Manager 上增加自动游戏检测，沿用现有鉴权、卸载和显存监控，**没有新增 Python 依赖**。

功能已通过离线测试和本机模拟进程验收；用户的真实游戏 EXE 名称尚未提供，因此实际配置保持“检测关闭、白名单为空”。模拟验收通过不代表已经为 CS2、《红色沙漠》或其他真实游戏启用了保护。

手动管理、令牌生成及本机 CLI 的基础用法见 [GPU 管理说明](./gpu-resource-manager.md)。

## 它怎样判断游戏正在运行

检测器使用 Windows 的 `tasklist.exe /FO CSV /NH`，比较进程的 EXE 文件名与用户提供的白名单。它不根据 GPU 利用率猜测游戏，也不查找安装目录、读取进程命令行或窗口标题。

进程名称统一忽略大小写；白名单中的重复名称只保留一份。只要任意一个配置的 EXE 正在运行，就触发自动来源的 GAMING。这里只比较名称，同名的其他 EXE 也会匹配，因此应选择实际游戏进程，不要把浏览器、Steam 启动器或通用 Python 解释器加入游戏白名单。

启动时先完成第一次扫描，再开放后端服务；扫描尚未确认时，本地模型入口保持锁定。之后每次巡检完成后等待配置的 5～10 秒，再执行下一次扫描。进程读取最多等待 5 秒，卸载和排空已有推理也需要时间，因此这不是游戏启动瞬间的系统级隔离。

检测到游戏后，管理器先锁住受控推理和唤醒入口，再沿用第一轮的排空、Ollama 卸载、`/api/ps` 复核与显存采样。检测器只负责触发调度，不通过清理 Python 变量、结束进程或修改显卡驱动释放显存。

## 先取得真实 EXE 名称

1. 手动启动你要配置的游戏。
2. 按 `Ctrl+Shift+Esc` 打开 Windows 任务管理器，进入“详细信息”页。
3. 找到实际游戏进程，记录“名称”列完整的 EXE 文件名。不要使用桌面快捷方式名称，也不要从游戏中文标题推测文件名。
4. 有多个游戏时，分别记录各自的真实名称。这里只需要文件名，不需要发送安装路径或账号信息。

目前没有预置或猜测任何游戏 EXE。未确认名称时，继续使用手动 GAMING 即可。

## 配置方式

安全默认值为：

```dotenv
NOVA_GPU_GAME_DETECTION_ENABLED=false
NOVA_GPU_GAME_PROCESSES=[]
NOVA_GPU_GAME_POLL_SECONDS=5
```

| 配置项 | 作用 |
| --- | --- |
| `NOVA_GPU_GAME_DETECTION_ENABLED` | 显式开启检测，默认关闭 |
| `NOVA_GPU_GAME_PROCESSES` | JSON 数组，只能包含 EXE 文件名；默认空数组 |
| `NOVA_GPU_GAME_POLL_SECONDS` | 巡检等待间隔，必须为 5～10 的整数，不接受布尔值 |

开启检测前，必须已启用 `NOVA_GPU_ENABLED`、配置有效的本机管理令牌，并提供非空白名单。已有 GPU 管理的回环监听、单 worker 和访问权限要求保持有效。

取得真实名称后，可以在准备启动后端的同一个 PowerShell 中设置以下进程环境；示例会让你自己输入名称，不预设游戏：

```powershell
$taskGameExe = Read-Host '输入任务管理器中确认的游戏 EXE 文件名'
$env:NOVA_GPU_GAME_PROCESSES = ConvertTo-Json -InputObject @($taskGameExe) -Compress
$env:NOVA_GPU_GAME_POLL_SECONDS = '5'
$env:NOVA_GPU_GAME_DETECTION_ENABLED = 'true'
```

多游戏配置使用包含多个真实文件名的 JSON 数组。只填文件名；路径、通配符、空元素及非法文件名字符会被拒绝。不要把这些配置直接覆盖写入已有 `.env`，也不要将真实管理令牌写入示例或 Git。

配置在应用启动时读取。已有后端需按其正常退出流程关闭，再从带有上述环境的终端启动；不要并行开启第二个调度实例，也不要为了刷新配置直接结束任意 Python 进程。仅修改当前终端的环境变量不会改变已经运行的服务。

## 游戏关闭后为什么还保持 GAMING

游戏消失后，第一次成功的“未检测到游戏”扫描开始计算退出窗口。需要连续 60 秒没有再次发现游戏，自动来源的保护才可以解除。

- 游戏再次出现：退出计时归零，继续 GAMING。
- 扫描失败或快照不可靠：状态视为未知，退出计时归零；不能把读取失败当作游戏已经关闭。
- 满足退出窗口：只有自动来源的保护可以解除；恢复 AUTO 本身不预加载模型，也不恢复训练。

60 秒在成功扫描时确认，因此最终恢复通常发生在满足条件后的下一次巡检，不保证恰好在第 60.000 秒切换。

如果用户手动选择了 GAMING，或者显式调用了 `/unload`，手动来源的锁会一直保留；游戏退出和检测器恢复都不能代替用户解除它。此时需先确认游戏检测保护已解除，再手动选择 AUTO。

检测到游戏、正在等待退出窗口或扫描故障时，手动请求 AUTO 会被拒绝，不能借此绕过自动保护。游戏期间推理与唤醒仍返回 423，不自动调用 DeepSeek。

## 重启和故障处理

模式文件同时保存手动来源和自动来源。服务重启时先保持本地入口锁定，再扫描；若上次保存了自动游戏保护，即使重新启动后第一次没有发现游戏，也要重新等待完整退出窗口，不把关机期间当作已经成功扫描的缺席时间。

如果把检测功能关闭，但上次保存的自动游戏保护仍在，管理器会要求人工确认恢复，而不是通过关闭检测绕过已有保护。旧版只保存 GAMING 的模式文件也保守保留为手动来源。

同一个连续保护阶段只触发一次自动卸载尝试；后续巡检不会反复加载或反复卸载。扫描恢复不会自动唤醒模型，卸载失败也不会自动回到 AUTO。

出现异常时：

1. 查询受保护的 `/api/gpu/status`，区分扫描错误、模型服务不可达和卸载失败。
2. 修复实际原因并等待成功扫描；游戏已经退出时，仍需重新完成退出确认窗口。
3. 如有卸载故障，确认 Ollama 和原推理已正常结束，再显式执行卸载复核。
4. 自动保护已解除后，如仍保留手动锁，再手动恢复 AUTO。不要删除安全状态文件绕过锁定。

后端关闭时停止检测任务，再清理 GPU 管理器和数据库；不关闭其他程序或强制中断训练。

## 查看状态

继续使用相同鉴权的 `GET /api/gpu/status`，或在已配置同一令牌的终端运行：

```powershell
.\.venv\Scripts\python.exe harness\gpu_cli.py status
```

| 字段 | 含义 |
| --- | --- |
| `mode` | 当前 AUTO 或 GAMING |
| `mode_source` | 当前主要来源：`manual`、`game_detection`、`safety` 或 `auto` |
| `manual_gaming` | 用户手动来源的保护是否仍在 |
| `detected_gaming` | 检测器保护是否仍在；包含启动待确认、退出等待和扫描故障，不只表示此刻发现了游戏 |
| `game_detection.enabled` | 是否启用了检测功能 |
| `game_detection.state` | `starting`、`game_detected`、`exit_grace`、`monitoring`、`scan_failed` 或关闭时的 `disabled` |
| `game_detection.ready` | 最近扫描是否成功；为 true 不代表退出窗口已完成 |
| `game_detection.matched_processes` | 本次命中的白名单名称，不是电脑全部进程清单 |
| `game_detection.last_scan_at` | 最近扫描的 UTC 时间 |
| `game_detection.clear_for_seconds` | 当前连续成功缺席窗口已持续的秒数 |
| `game_detection.error` | 扫描错误代码；失败时不能把空的命中列表当作“游戏已退出” |
| `game_detection.last_action_error` | 最近自动控制操作的错误代码，需结合管理器 `fault` 查看 |

模型是否真正卸载，仍要结合 `backend.models`、`unload_verified` 和显存/计算进程采样；不能只看 `mode` 或显存下降。运行记录只保留必要状态、时间及命中的配置名称，不输出完整进程列表、请求正文或认证令牌。

## 验收记录与边界

本轮全量离线测试266项通过、0失败、0跳过（4.98秒）；Ruff静态/格式及工程自检通过。本机15项真实验收使用自有模拟EXE、真实Windows进程读取、Ollama、5秒巡检和完整60秒退出窗口，实际成功缺席确认63.237秒，未用加速时钟冒充等待。未启动真实游戏，也未修改用户的游戏白名单。

显式实测程序为 `harness/verify_game_detection_live.py`；每次必须使用不存在的新输出目录。它只创建并正常退出自己的模拟进程和验收后端，不终止用户程序、不调用收费服务。证据位于：

```text
E:\NovaAILab\logs\gpu-game-detection-20261101-040957-872\live-1\report.json
```

一次卸载采样为5716→1937MiB，且模型清单为空；退出确认后AUTO仍没有驻留模型。检查命令与全量证据见 [阶段验收](ACCEPTANCE.md) 和 [构建记录](../build-log.md)，不能用模拟进程测试宣称真实游戏已完成配置。

**保护范围仍是经 Nova 管理器发起的请求。** 外部程序直接访问 Ollama 的 `127.0.0.1:11434` 仍可能重新加载模型，原 Lab 直接推理示例也可以绕过门禁。游戏检测不是 Windows 层面的 GPU 独占或防火墙隔离。

本轮未实现独立的三分钟空闲休眠任务、训练启动互斥或安全检查点暂停、AI_FOCUS、vLLM Sleep Mode、云端回退和图形界面。`training.state=idle` 表示没有登记训练租约，不代表没有外部训练或训练已经暂停；游戏结束后也不会自动恢复训练。

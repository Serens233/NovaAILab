# Nova 技术决策记录

## V3实验模型（2026-11-01）

复用原模型注册表、客户端、GPU控制器及聊天协议，只增加可选HF实验项和配置；默认仍为9B，云端不自动回退。16GB系统RAM阶段先下载，物理RAM准入独立于显存准入，拒绝发生在驱逐稳定模型前；实验关闭或RAM低仍允许卸载。大小写等价名称不能绕过策略。

使用标准库GlobalMemoryStatusEx读取物理内存，未知时关闭实验加载，不通过分页文件容量伪装可用RAM；默认最低28GiB物理及18GiB可用，升级32GB后也须实测。GPU层数默认省略交由Ollama决定部分卸载，不强制全GPU。上下文4096、单模型、原空闲卸载不变。不加依赖、Strata、训练或长期记忆框架。普通JSON只通过新增可选stream=false适配，不改前端默认SSE。来源、边界和重评估条件见[部署说明](qwen38-deployment.md)。

## Nova V2（2026-11-01）

保留原FastAPI/SQLite/Python3.14与GPU状态机；独立frontend使用Next.js/React/TypeScript及MIT的assistant-ui。优先执行官方CLI，下载模板超时后改取官方最小模板必要文件，未安装参考仓库或保留默认OpenAI后端。LocalRuntime/ChatModelAdapter适配Nova自定义SSE，线程/历史适配器读取FastAPI权威数据，不假设兼容AI SDK协议。

前端依赖在自己的package-lock中锁定，不加入Python训练环境；Node24.22.2便携包从nodejs.org下载并校验官方SHA256，无系统PATH/管理员变更。Python流式传输使用标准库，不新增Python依赖。具体包版本与实际安装/测试记录在V2验收文档。

SQLite仍使用同一个文件与Database.session，加表前执行backup API完整备份；基础user_version=1保留，nova_chat_schema单独记录扩展version=1，避免改变禁用聊天时的原基础契约。已有不兼容同名结构拒绝覆盖；重启pending明确标interrupted。后端拥有消息与幂等请求，前端history.append不二次插入。

Next只代理固定接口到127.0.0.1 FastAPI，服务端Bearer不进入浏览器；原GPU CLI的Origin/回环限制保留。云端需服务端显式开关、密钥及单次明确同意，不自动收费回退。本轮不实测收费API。手机只验收响应式布局，默认监听仍为回环；局域网/公网访问另需认证及部署设计。

模型注册表初版仅9B/4B/DeepSeek。9B与4B是Ollama推理量化权重，4B BF16 LoRA是未来训练目标，本轮不下载BF16训练权重或修改训练环境。每次本地加载由原GPU Manager检查模式和实际显存；空闲180秒用原卸载/复核路径，不调用empty_cache代替卸载。

## 无白名单升级（2026-11-01）

采用独立标准库Win32/PDH/DXGI采集、平台元数据缓存和纯规则分类器，而不整装第三方项目/引入psutil/ETW。五项目版本、许可及不复制处理见 [升级说明](automatic-game-detection.md) 的研究链接。

新信号源复用原GameDetector/Manager，不复制卸载实现；目标EXE不硬编码。连续确认和完整进程身份降低抖动，负向分类先于正向索引；不把DLL/全屏/高GPU任一单项当游戏。压力来源独立，只在空闲卸载并保存原因/重载余量。

Windows预算只记录采样进程口径，不冒称全局或其他进程可用预算。默认新开关关闭、旧模式兼容，用户自行选择实机启动时机。真实游戏/FPS和压力高负载待后续验证，不因411项代码回归通过而作全场景保证。

状态：保留历史决策，按用户授权追加V3 Phase 2决策。具体安装、锁定版本和执行结果以 [开发进度](progress.md) 和 [阶段验收](ACCEPTANCE.md) 为准；设计决策本身不代表验收已通过。

## 记录方式

重要决策按“选择、理由、影响、重新评估条件”记录。新增依赖和架构变更应先说明，再实施；数据库破坏性操作另需备份方案及用户明确授权。后续改变应新增或更新有日期的决策，说明替代关系，避免静默修改设计前提。

D001–D010 保留 Phase 0 时点的决策；其中仅适用于该阶段的“无业务依赖、无构建后端、不创建数据库”等限制，由 D011–D015 明确演进，不能误作当前阶段状态。

## D001：模块化单体与按阶段交付

- **选择**：一个 Python 后端，采用职责明确的模块；Web 优先，Flutter 后续复用 API。Phase 0 只建立工程基础，不实现业务功能。
- **理由**：当前是个人助手早期项目，单实例和单用户需求不需要分布式协调成本。
- **影响**：不提前引入微服务、消息队列、通用 Agent 框架、复杂依赖注入容器或插件协议。未来目录只在需要时创建。
- **重新评估条件**：出现可量化的独立扩缩容、部署隔离或复杂任务生命周期需求。

## D002：CPython 3.14 基线

- **选择**：`pyproject.toml` 约束 `>=3.14,<3.15`；`.python-version` 精确固定 `3.14.10`，采用常规带 GIL 的 CPython。安装由 uv 管理。
- **理由**：3.14 已有稳定维护周期，提供现代标准库与类型语法；限制到同一小版本系列可减少开发差异。支持周期依据 [Python 官方版本状态](https://devguide.python.org/versions/)。
- **影响**：新成员按版本文件安装；补丁升级需同步版本文件、记录实际解释器版本并重新验证。uv 托管解释器来自 Astral 的 `python-build-standalone`，来源见 [uv 官方安装说明](https://docs.astral.sh/uv/guides/install-python/)。
- **重新评估条件**：关键运行依赖不支持该版本、补丁安全更新发布，或部署环境存在已验证的版本限制。不得因安装失败静默降级。

## D003：uv 与单一依赖来源

- **选择**：使用 `pyproject.toml` 声明直接依赖，提交实际生成的 `uv.lock`，用 `uv sync --locked` 复现环境。Phase 0 以非发布项目运行，不增加构建后端依赖。
- **理由**：统一 Python、虚拟环境、依赖解析和锁定工作流，减少手工 pip 安装造成的环境偏差。命令语义见 [uv 项目锁定与同步](https://docs.astral.sh/uv/concepts/projects/sync/)。
- **影响**：不手写锁文件，不另维护容易漂移的 `requirements.txt`。需要升级时显式更新约束或锁定结果，再验证。锁文件不代替解释器版本与操作系统记录。
- **重新评估条件**：需要发布 Python 包时配置构建后端；外部部署工具确实要求其他格式时从锁文件导出，而非建立第二套手工依赖清单。

## D004：pytest 与 Ruff 开发依赖

- **选择**：仅新增 `pytest>=9,<10` 和 `ruff>=0.14,<1` 两项直接开发依赖，放入开发依赖组；精确解析版本以 `uv.lock` 为准。Ruff 同时负责格式化、导入排序与适度静态检查。
- **理由**：pytest 为未来行为测试提供统一入口；Ruff 覆盖本阶段格式和常见静态问题，避免同时维护多个格式化工具。
- **影响**：新增工具会下载相应直接及传递依赖。Phase 0 没有业务用例，不能把无测试或 pytest 退出码 5 作为通过；工程自检使用 Python 标准库完成。
- **重新评估条件**：实际复杂度要求类型检查、异步测试或覆盖率工具时，先说明新增工具能发现的具体问题与验证方法。没有需求时不安装插件。

## D005：FastAPI 为后端传输层

- **选择**：后续以 FastAPI 提供 HTTP API，Agent 核心不依赖 HTTP 请求对象；运行时依赖在实现阶段再引入。
- **理由**：满足 Python Web 后端与清晰 API 的技术方向，同时保留 CLI 或 Flutter 等消费方式的空间。
- **影响**：Phase 0 没有启动入口或服务启动命令。后续需按实际 API 需求说明并安装 FastAPI、服务运行器和配置工具，新增必要的接口测试。
- **重新评估条件**：存在具体协议或运行环境要求；调整前须评估客户端和核心编排的影响。

## D006：SQLite 与集中存储访问

- **选择**：初期使用 SQLite，所有数据访问集中在存储模块；本阶段不创建数据库，不安装 ORM 或迁移工具。
- **理由**：单用户、单实例部署可以避免独立数据库服务的安装与运维成本。
- **影响**：首次持久化阶段需决定连接生命周期、同步或异步接入、事务、schema 版本、备份与恢复。标准库是否足够由实际访问需求决定，不能在异步请求循环中直接进行阻塞访问。
- **重新评估条件**：实际并发写入、锁等待、跨实例部署或数据运维要求超出 SQLite 可接受范围。迁移必须包含数据验证与回退方案。

## D007：DeepSeek 首个 Provider，契约隔离供应商

- **选择**：DeepSeek 为首个接入目标；以普通 Python 数据结构和小范围接口封装模型调用，不把供应商 SDK 类型传播到业务核心。
- **理由**：符合 API 优先级，并减少未来更换供应商对人格、记忆和工具流程的影响。
- **影响**：实际接入前核实官方接口、模型标识、限流、流式与工具调用能力；依据需求选择 SDK 或 HTTP 客户端。Phase 0 不联网调用模型、不要求用户填写 API Key，也不预装 SDK。
- **重新评估条件**：增加第二个 Provider、模型能力差异或供应商协议变化。此时扩展必要契约并增加相应兼容性测试。

## D008：人格与记忆分离

- **选择**：人格作为版本化规则；记忆作为带来源、时间且可修正的数据；普通记忆不能覆盖权限和安全规则。
- **理由**：稳定人格需要可追踪的变更，长期记忆需要纠错与遗忘能力，两者生命周期不同。
- **影响**：在首次记忆实现时交付查看、写入、检索、纠错和删除语义。当前不引入向量数据库或自动全量保存对话。
- **重新评估条件**：实际检索质量不足、人格配置出现明确的多版本管理需求或隐私保留策略变化。

## D009：密钥、隐私与工具权限边界

- **选择**：真实凭据仅从本地环境或被忽略的 `.env` 加载；示例密钥留空。默认日志不记录完整用户内容。工具执行单独校验参数、路径与用户授权。
- **理由**：陪伴和长期记忆涉及个人信息，模型提出动作的能力不等于执行授权。
- **影响**：`.gitignore` 排除本地配置、数据库、日志和运行数据；提交前仍需审查差异。工具和外部内容不能修改信任规则。若泄密必须撤销并轮换凭据，删除文件不足以恢复安全。
- **重新评估条件**：公开部署、接入外部写操作或扩大数据范围时，先补充鉴权、日志脱敏和保留策略，并验证相应行为。

## D010：Windows 本地优先，VPS 后续验证

- **选择**：当前使用 PowerShell 和项目内虚拟环境，通过 `uv run` 执行命令；不要求激活脚本或永久放宽系统执行策略。VPS 部署放在独立阶段。
- **理由**：符合当前开发环境，减少 Windows 执行策略及多解释器路径歧义。
- **影响**：文档需提供准确工作目录、安装来源、PATH 问题处理和真实可运行的工程检查命令；不提前引入 Docker、生产进程管理或公网暴露。
- **重新评估条件**：准备实际部署时，再验证 Linux 兼容性、TLS、鉴权、备份和恢复；本地通过不等于生产就绪。

## D011：Phase 1 范围调整（2026-10-27）

- **选择**：按用户新指令仅实现后端基础架构，替代原 Phase 1 的 DeepSeek + Web 对话闭环；Python、FastAPI、SQLite 与模块化单体方向不变。
- **理由**：先验证生命周期、配置、安全错误和存储基础，再引入模型与用户业务。
- **影响**：本阶段不调用 DeepSeek、不开发聊天、前端、记忆或业务表；后续业务切片由用户重新发起并确认。
- **重新评估条件**：用户明确开始下一阶段时，重新确定范围及依赖；路线图不自动授权执行。

- **选择**：从 Phase 0 `non-package` 演进为 `src/nova` 可编辑应用包，使用 `uv_build>=0.13.6,<0.14`，模块名为 nova；不发布包。
- **理由**：使测试和 `python -m nova` 使用一致导入方式，避免手工设置 PYTHONPATH；保留 uv 单一环境管理流程。
- **影响**：`uv sync --locked` 安装本地项目；uv 版本限定为 `>=0.13.6,<0.14`，与当前安装和构建后端匹配。Phase 0 的“无构建后端”是该阶段状态，不再作为后续检查限制。
- **重新评估条件**：需要发布、原生扩展或新的构建需求时重新评估；不为本阶段增加其他构建工具。[uv 官方说明](https://docs.astral.sh/uv/concepts/build-backend/)

- **选择**：新增 FastAPI、Uvicorn、Pydantic、Pydantic Settings；显式声明直接使用的 Starlette；开发组新增 HTTPX2 支持当前 TestClient。精确版本以 uv.lock 为准。

- **影响**：新增必要传递依赖；pytest 9.1.1、Ruff 0.17.3、CPython 3.14.10 与 uv 0.13.6 保持不变。不安装模型 SDK、ORM、迁移框架或监控服务。
- **重新评估条件**：依赖兼容、安全维护或明确新增功能要求变化时，先说明用途和验证方法，再显式更新锁文件。

初次以 HTTPX 0.28.1 验证时，新版 Starlette 的 TestClient 给出弃用提示；核对 [官方 TestClient 文档](https://starlette.dev/testclient/) 与已安装包依赖后，改用其当前支持的 HTTPX2。该兼容性调整只涉及本阶段刚引入的测试依赖，不升级 Phase 0 工具，也不屏蔽警告。

## D014：sqlite3 会话与非破坏性初始化（2026-10-27）

- **选择**：标准库 sqlite3，每个会话在同线程完成连接、操作、事务和关闭；管理器只保留路径、超时及状态，异步入口通过线程调用完整操作。
- **理由**：当前没有业务模型或复杂查询，无需 ORM；避免跨线程共享连接及同步 I/O 阻塞异步事件循环。
- **影响**：初始化幂等，`application_id=0x4E4F5641` 与 `user_version=1` 标识 Nova 元数据基线，不建业务表；未知结构、外部 application_id、损坏文件和未来版本失败关闭，不清空已有数据。显式初始化命令和服务启动使用同一逻辑。
- **重新评估条件**：首次业务 schema、并发写入或部署需求出现时再决定迁移工具和连接策略；WAL 等策略必须单独验证。

## D015：安全错误与日志（2026-10-27）

- **选择**：统一错误代码、中文提示和请求标识；标准 logging 使用 JSON 控制台格式，同时约束应用与服务器日志，关闭原始访问日志，避免请求体、认证头、原始查询参数和异常敏感值。
- **理由**：配置、校验异常及 ASGI 服务器重复记录异常都可能泄露输入，仅隐藏客户端堆栈不足够。
- **影响**：配置失败只报告安全字段提示；健康响应不暴露数据库路径；使用合成敏感值验证客户端和日志。监控接入保留 logger/handler 扩展方式，当前不引入监控平台。
- **重新评估条件**：上线、审计或排障需求变化时评估记录内容、脱敏与保留期；不得通过开启原始请求日志绕过规则。

## D016：GPU 管理第一轮（2026-11-01）

- **选择与理由**：在现有模块化单体增加独立 GPU 管理器和窄 Backend Protocol，不重建应用。沿用 Python3.14/uv/FastAPI，标准库 HTTP 和 subprocess 完成受限本机调用，无新依赖。
- **游戏优先**：先保存 GAMING 并关闭 admission，再等待既有请求、逐个卸载与轮询状态；任何不确定结果保持锁定。AUTO 仅解除门禁，不自动预载。
- **并发及退出**：后台操作通过 shield 与任务集合跟踪，客户端取消不能提前释放活动计数；控制任务未完成也不能释放 OS 租约。AUTO 入锁后再次检查 GAMING 排队状态，避免排队请求覆盖更高优先级控制。
- **安全与状态**：默认关闭、仅回环监听、Bearer 随机令牌、拒绝浏览器 Origin、单 worker/同 Ollama 单实例。模式与未确认标记原子持久化，元数据日志不写正文或认证。
- **边界**：受控 `/api/gpu/generate` 只用于本轮门禁验收，不是聊天业务。无收费回退、外部训练暂停或 GPU 进程强杀。直连11434仍能绕过门禁；不能把此接口当作全系统GPU隔离。
- **验收**：194项离线测试及17项真实本机检查通过。后续有明确游戏进程配置、训练检查点契约后再扩展；vLLM仅保留接口，不安装、不暴露开发管理端点。

## D017：用户白名单和独立来源的游戏检测（2026-11-01）

- **选择**：Windows官方tasklist、标准库CSV/subprocess/to_thread，不新增psutil；仅处理名称与PID，不读取命令行/窗口或猜测游戏名。名单来自用户确认，默认关闭且为空。
- **来源**：手动GAMING和检测hold分开持久化；旧GAMING状态保守迁移为手动。AUTO不得越过检测hold，自动退出仅释放自身来源。
- **时间和故障**：5–10秒串行扫描、单调时钟连续成功缺席60秒；匹配/失败重置计时，重启后重新等待。首扫前关闭入口，故障只触发一次卸载尝试，不反复加载或卸载。
- **生命周期**：首扫读取已加载的保存状态；stop后忽略迟到快照，退出先停检测再清理管理器与DB。没有自动恢复训练或预加载模型。
- **验证与重评估**：266项回归、15项真实模拟进程/Ollama检查通过。名单变更在重启后端后生效；未来确有热更新或非Windows需求时再扩展，不把进程名检测当作整机GPU隔离。

## D018：卸载任务所有权与未知资源策略（2026-11-02）

- **问题与目标**：关闭管理器不能遗失仍在运行的卸载线程，未知模型不能因策略缺失跳过资源准入；保留现有游戏优先状态机。
- **约束**：`asyncio.to_thread` 的线程不会随等待任务取消而结束；单一 Ollama 服务由同用户单实例租约保护，模型管理不接管或杀死训练进程。
- **方案与接口**：区分等待/退避回收与已进入卸载 I/O 的回收；后者纳入 `close()` 的有界等待，超时持久化 `uncertain` 并保留实例租约，真实结束后可再次关闭释放。`chat`、`wake`、`generate` 的目标都必须匹配显式受校验策略，未知模型及自定义别名返回 `MODEL_POLICY_INVALID`；注册表和调度器继续共享稳定模型策略与实验模板。
- **备选与权衡**：取消所有 Future 无法停止真实线程；无限等待会阻塞正常关闭；按模型名字猜测内存占用不可验证。因此选择有界关闭、超时保持锁定，以及未知策略默认拒绝。
- **风险**：上游永久失去响应时实例会保守锁定；自定义模型必须先显式登记资源策略。测试替身也需登记合成策略，不在生产代码增加测试环境绕过。
- **验收**：真实 `to_thread`/Event 替身验证卸载未结束时第二实例不能启动，线程结束后可正常释放；未知模型三入口在任何后端调用前拒绝；已有流式、取消、游戏、训练及幂等回归通过。真实游戏与性能结果单独记录，不能由替身测试代替。

## D019：响应头前的截止线与取消（2026-11-02）

- **问题与目标**：逐次 socket 超时无法限制持续缓慢发送的响应头；只在收到响应头后绑定取消句柄，会让故障请求持续占有推理与游戏排空流程。
- **约束**：保持现有标准库 HTTP、固定回环/HTTPS目标、无代理/无重定向、流大小和思考隔离；不新增运行时依赖或改变公共 API。
- **推荐方案**：本机 HTTPConnection 建连后立即向 StreamControl 登记 socket，响应头和正文都受同一截止线；流前安装预检共享剩余期限与取消控制。云端 HTTPS 显式建连后、发送请求与读取响应头前绑定 socket。
- **接口约定**：新增内部 `StreamControl.bind_socket()`，`_request()` 可接收上层 control/deadline；ModelBackend、HTTP/SSE 与数据库 schema 不变。取消等待任务不等于线程结束或显存释放，资源跟踪仍由管理器负责。
- **备选与权衡**：只给 Future 增加超时会遗留真实线程；只设置每次 recv 时限仍可被慢速头绕过；更换完整 HTTP SDK 会引入依赖和更大迁移。此次只补连接所有权与期限。
- **风险**：DNS解析由操作系统控制，socket超时不能提供DNS硬期限；TCP/TLS建立使用连接超时，连接返回后检查取消/到期标志，阻止继续发送。云端180秒不能解释为包含系统DNS解析的绝对保证；升级CPython或输运实现时须重跑边界测试。
- **验收**：9 项本机合成慢头/慢正文/预检/Stop/云替身测试在旧实现全失败，修复后通过；相关 165 项与全量 818 项通过，无真实收费 API。真实模型、空闲与游戏分别留存证据。

## D020：只读三层人格与纯上下文编排（2026-11-02）

- **问题和目标**：将用户已确认的Nova最小身份与表达风格独立于Provider保存，避免聊天或模型输出直接改写人格；在不改GPU状态机和聊天协议的前提下提供可追溯上下文。
- **当前约束**：单机单管理信任域，现有FastAPI、SQLite、ChatService、13条API路径和SSE继续使用；GPU检测/休眠/卸载/优先策略冻结。本轮无27B、后台模型任务、私人数据训练、运行时审批服务或Phase 3记忆，不新增依赖。
- **推荐方案**：包内JSON保存版本化Canon与Persona，固定manifest记录文件SHA256，manifest自身SHA256固定在代码中。来源限项目负责人批准，只有`approved`特征进入深度不可变快照。`NOVA_PERSONA_CONFIG_DIR`为空使用包内版本，外部目录也必须满足同一信任根；坏配置安全拒绝，坏reload不覆盖原合法快照。
- **核心接口与状态约定**：`PersonaManager.snapshot()`只读，`reload()`完整校验后原子发布；运行时Canon写入、提案审批与应用均拒绝。Dynamic State默认TTL900秒、最多256会话，进程内更新/reset，不存用户永久事实。提案只保留来源、证据、目标、基准版本和验证结果，`validated`不授予批准权。人格变更或回退通过源控审查、匹配的bundle/代码pin和重新部署完成。
- **上下文约定**。安全及权限规则优先于 Canon，Canon 优先于已批准 Persona。临时状态、历史和用户或模型文本仍是对话数据。`ConversationOrchestrator.build()` 只构建消息，ChatService 保留执行生命周期。默认上下文 4096、输出保留 512，估计为 UTF-8 字节数加每消息 32 及总余量 128。最多保留 20 条历史消息，按完整轮次裁剪较早内容。临时状态使基础预算超限时省略，核心和当前消息仍超限则返回 422。回退到备用模型时按实际预算重新编排，并记录实际模型的指标。
- **备选与权衡**：把人格直接写入SQLite或提供通用更新路由会提前引入审批、并发版本、认证和恢复问题；仅检查JSON内自报`approved`不能建立信任；引入每模型tokenizer增加本轮依赖与模型分支。因此选择源控信任根、只读内部契约和保守预算，完整成长及精确tokenizer后续另行决策。
- **风险**：代码pin保护受控部署配置，不抵御已能改写源码的本机管理员；提示隔离不能仅凭模型口头回答证明安全。会话隔离不是多用户认证；临时状态重启丢失是预期行为。字节估计可能过早拒绝长消息，不能当精确token计数或所有模型模板的数学保证。
- **验收条件**：覆盖未授权写入、伪审批、摘要/版本/结构篡改、pending不生效、深度不可变、坏reload保留、TTL/容量/隔离、完整轮次裁剪及422边界；重跑聊天/取消/游戏/资源回收和API回归。包构建须验证JSON被完整包含并保持hash；真实9B/4B固定合成题集经Nova API执行、原始证据外置，协议结果与人工角色质量分别验收。实际结果由本阶段验收文档记录，不在本ADR预判通过。

## D021：实例互斥、聊天一致性与逐次授权（2026-11-04）

- **问题与目标**：不同 TEMP 导致同一 Ollama 服务启动多个调度器；并发准备可能使用过期历史；存储异常可能留下无法恢复的待处理任务；界面不能重复沿用云端授权。
- **约束**：沿用单机、单管理信任域、现有 SQLite schema 和 GPU 状态机；不引入依赖、不读取私人聊天、不自动调用云端。
- **方案与接口**：Windows 用全局命名内核对象的存续期实现实例租约，不依赖线程所有权；Linux 使用当前用户目录的锁。训练预留中断后只允许相同 job_id 和资源需求取回已预留租约，游戏及未知状态继续拒绝。读取最近完整回合、校验上下文与预留任务在同一写事务中完成；失败保存暂存在进程内、使用原任务幂等重试。云端发送每次单独确认。
- **备选及权衡**：仅调整 TEMP 环境变量无法跨环境互斥；保存失败后直接标为成功会误导用户；无限重试或直接释放训练租约可能损坏状态。采用保守拒绝和有界恢复，保留失败的明确状态。
- **风险**：升级时旧 TEMP 文件锁与新版命名对象不互认，必须先正常停止全部旧管理器并等待未结束的推理与卸载，再启动新版；Linux 锁不保证跨用户互斥。未落库回复的进程内恢复最多 128 个占位，进程终止后只能将未完成任务标为中断；上下文 dropped_messages 仅统计所读取窗口内的裁剪。回环网关不是多用户认证。
- **验收条件**：真实跨 TEMP 子进程锁与跨线程释放、训练预留取消及游戏竞态、历史并发屏障、保存失败和幂等恢复、云端逐次确认与拒绝不发送均覆盖；真实游戏、模型和性能单独记录。
